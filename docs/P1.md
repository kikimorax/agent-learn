### P1-01 一次模型请求与 Message / Instruction

**要解决的问题：** 同一句总结要求，为什么不同写法会得到不同结果？

**概念与掌握程度：** Message 是有角色和内容的一条消息；Instruction 是内容中的行为要求。消息还可携带材料，二者不是互斥类型。

**本课用到的库：** OpenAI 客户端的 chat.completions.create；messages、choices；只学习当前调用路径。

**阅读入口：** [Prompt 示例](../P1/examples/gpt_prompt_eng_l2-guidelines.py) 的 get_completion；[客户端](../P1/examples/openai_client.py) 的 create_client；[Prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering) 阅读 Message roles and instruction following。

#### 必做｜完成本课

1. 沿 get_completion 找到消息构造、请求发送与回复提取。
2. 用本课第一课入口中的固定图书馆文本做两次总结：无格式约束、三条且每条不超过 30 字；检查是否遗漏或新增事实。

**通过标准：** 保存两组请求和结果；能区分 Message、指令与材料，指出一项可自动检查的规则。

**理解检查：** 逐项检查条数、长度、遗漏和新增事实；格式可由代码检查，语义需要人工核对。

### P1-02 上下文、token 与采样

**要解决的问题：** 第二轮为什么会忘记上一轮说过的话？

**概念与掌握程度：** 上下文是本次实际发送的信息；token 是模型处理单位，不等于汉字数；上下文窗口有限。采样影响输出分布，不保证正确性。

**本课用到的库：** messages 列表、响应 usage、temperature；不学习模型训练和 tokenizer 实现。

**阅读入口：** 上课的 get_completion 每次只发送一条消息；[Prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering) 阅读 Planning for the context window。

#### 必做｜完成本课

1. 用“项目代号是青禾”做两轮对话，对比不带历史与携带历史。
2. 查看一次 usage，缺失时标未知；解释 token、窗口和采样的用途，不要求多参数重复实验。

**通过标准：** 两份消息列表及结果；能解释忘记信息的原因，不把字符数当 token。

**理解检查：** 删除信息与压缩信息的区别；temperature=0 也不作为逐字复现保证。不要通过塞满超长输入制造不必要调用。

#### 巩固｜不熟练时再做

设计一条上下文保留规则，保留当前任务与必要事实，丢弃无关闲聊。

沿用本课输入或换一个小例子，能独立完成即可；不新增强制报告，不阻塞进入下一课。

### P1-03 明确约束与 Few-shot 对照

**要解决的问题：** 加长 Prompt 是否一定改善结果？

**概念与掌握程度：** Zero-shot 没有任务示例，Few-shot 提供示例；约束明确目标和成功条件。示例要覆盖规则，不能泄露测试答案。

**本课用到的库：** 复用 get_completion；Python 列表保存输入，perf_counter 计时。

**阅读入口：** [guidelines](../P1/examples/gpt_prompt_eng_l2-guidelines.py) 的 p1_t4_few_shot_prompting；[iterative](../P1/examples/gpt_prompt_eng_l3-iterative.py) 的 issue1_limit_length；官方 Prompt engineering 阅读 Few-shot learning。

#### 必做｜完成本课

1. 对账单、技术、其他分类的同一组三个输入，比较无示例、明确标签约束、加两个示例三版 Prompt。
2. 保留错误输出，检查标签与含义，不只挑成功例子。

**通过标准：** 一张三版对照表，能说明每次只改变了什么。

**理解检查：** 一次只改变一类因素；不能仅展示优化后表现最好的问题。

加入“无法登录查看退款”这样的边界输入，先确定标签规则再评估。

### P1-04 JSON、Schema 与业务校验

**要解决的问题：** 合法 JSON 为什么还可能是错误研究任务？

**概念与掌握程度：** JSON 管语法，Schema 管字段与类型，业务校验检查请求含义；原生约束与本地校验各有职责。

**本课用到的库：** Pydantic BaseModel、Field、ConfigDict、model_validate_json、model_json_schema。

**阅读入口：** [P0 校验示例](../P0/examples/pydantic_demo.py) 的 demo_model_output；[Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) 阅读 How to use、Supported schemas、Refusals；[Pydantic Models](https://docs.pydantic.dev/latest/concepts/models/) 阅读 Validating data。

### P1-05 拒答、格式失败与有限修复

**要解决的问题：** 解析失败后，什么时候重试，什么时候停？

**概念与掌握程度：** 拒答、截断、格式不合法、网络失败是不同结果；有限修复只处理可修复的内容错误。

**本课用到的库：** ValidationError；显式状态和调用计数；用 Fixture 注入响应。

**阅读入口：** P1-04 自己实现的解析器（待实现）；Structured Outputs 的 Refusals；[现有客户端测试](../P1/tests/test_openai_client.py) 学习替换客户端。

#### 必做｜完成本课

1. 为格式错误最多修复一次，第二次仍失败就停止。
2. 用 Fixture 分别验证拒答与超时不会被当作合法任务；缺少主题时要求补充。

**通过标准：** 成功、修复成功、修复失败、拒答及传输失败路径可区分；总调用数有上限。

**理解检查：** 去掉围栏若作为兼容策略，必须记录预处理，不能把原始格式记为成功；拒答不计成合法任务对象。

#### 巩固｜不熟练时再做

让第二次回复仍然缺字段，验证总调用上限和明确失败说明。

### P1-06 普通输出与流式事件

**要解决的问题：** 屏幕上逐渐出现文字，与一次拿到答案有什么不同？

**概念与掌握程度：** 事件序列包含内容增量、终止和错误；先收到一部分文字不代表任务成功。

**本课用到的库：** 选定接口的 stream=True 与事件迭代；perf_counter；不混用 Chat 与 Responses 的事件结构。

**阅读入口：** [探针](../P0/examples/model_capabilities.py) 的 _probe_streaming；[Streaming responses](https://developers.openai.com/api/docs/guides/streaming-responses) 阅读 Enable streaming、Read the responses；选择 Chat 时对照探针对应分支。

#### 必做｜完成本课

1. 对同一简短请求观察普通回复与流式事件，拼接文本并识别完成信号。
2. 离线模拟中途断流，不能将已收到的部分文本记为成功。

**通过标准：** 保存一份事件序列和断流结果；能区分文本增量、结束与错误。

**理解检查：** 模型流式事件与 P6 的 HTTP SSE 转发是不同层；无结束信号不能标记成功。

#### 巩固｜不熟练时再做

### P1-07 固定评估集

**要解决的问题：** 怎样知道一次改 Prompt 是否真的更好？

**概念与掌握程度：** 数据集固定后才可比较；结构正确率、业务正确率和失败处理率不能混成一个数字。

**本课用到的库：** json / csv 保存结果；perf_counter；pytest 用于确定性检查，人工核对业务含义。

**阅读入口：** P1-03 的对照记录与 P1-05 的 Fixture（由前课产出）；[Evaluation concepts](https://docs.langchain.com/langsmith/evaluation-concepts) 阅读 Datasets、Experiment、Evaluators，仅借鉴概念，不要求云平台。

#### 必做｜完成本课

## 阶段项目

实现“研究任务解析器”：把自然语言研究请求转换为经 Pydantic 验证的 `ResearchRequest`，并在验证失败时提供清晰的修复流程，限制修复次数。

### 阶段项目增量约定

| 项目 | 要求 |
|---|---|
| 承接成果 | P0 的配置、能力报告、HTTP 排错习惯和 Pydantic 基础。 |
| 本阶段新增 | 将自然语言变成结构化 ResearchRequest，并对拒答、输入缺失和解析失败给出明确结果。 |
| 典型输入 | “用中文研究 2025 年本地 RAG，优先官方资料，最多检索 3 次。” |
| 预期行为 | topic=本地 RAG，time_range=2025 年，language=zh，source_requirements 包含官方资料，max_searches=3；表达可不同，含义必须一致。 |
| 失败处理 | 主题缺失需补充；明确非法预算不静默裁剪；内容格式最多修复一次；拒答、截断、超时和最终失败分别记录。 |
| 交付证据 | 解析器、输入输出约定、离线 Fixture 测试、至少 10 条固定评估输入和基线报告。 |

### ResearchRequest 练习约定

这是一份待实现的本地业务约定，不是对现有代码的描述：

| 字段 | 练习规则 |
|---|---|
| topic | 去除首尾空白后非空；用户没给主题时要求补充 |
| time_range | 用户指定的时间范围文本；未指定为 null，不擅自补日期 |
| language | zh 或 en；未指定时默认 zh |
| source_requirements | 字符串列表；未指定时为空列表 |
| max_searches | 1–10 的整数；未指定时默认 3，明确越界不静默改写 |

禁止额外字段。将本地模型转换为服务端 Schema 时，按所用接口的支持范围调整必需字段与 nullable 表达；原生模式不可用时明确标记降级为 Prompt + 本地校验。成功对象之外，区分“需补充信息、拒答、模型输出不合法、传输失败”，不把这些状态塞成虚假的研究任务。

### 评估指标口径

- 首次 Schema 合法率：正常及有效边界请求中，第一次生成就通过 Schema 的数量 / 这类请求总数；拒答、超时或未生成对象均不算通过。
- 修复后 Schema 合法率：同一分母下，最多一次修复后通过的数量 / 总数；保留首次结果，不覆盖原始失败。
- 业务正确率：同一分母下，最终对象符合原请求的数量 / 总数；有合法对象但主题或语言提取错误仍失败。
- 异常处理：对无效输入、拒答、截断、网络错误和修复失败逐类报告通过数 / 用例数；Fixture 检查与真实模型观测分开。
- 延迟统计覆盖首轮与修复总耗时；调用量包括失败和修复请求。每份报告写出分子、分母，不能只给百分比。

## 验收清单

本清单只验收必做主线。巩固和进阶可以不做；涉及测试“全部通过”时，指当前实现能力及必做边界的测试，不要求先实现所有扩展场景。若自行开放写入、网络访问等能力，其对应权限检查必须通过。

- [ ] 能解释上下文、采样和输出约束分别控制什么。
- [ ] 成功返回的研究任务全部通过 Schema 校验；固定测试集分别记录首次、修复后合法率和业务正确率，拒答、无效输入及最终失败按预期处理。
- [ ] 能用一组案例展示一次 Prompt 修改前后的效果，不只展示表现最好的案例。
- [ ] 能处理代理缺少原生 Structured Output 的情况，并明确记录降级方式。
- [ ] 已建立首版评估数据集和基线结果。

## 常见失败

- 输入输出约定尚不清晰，就试图靠加长 Prompt 解决问题。
- 把合法 JSON 误认为业务字段一定正确。
- 为了“可解释”要求模型暴露冗长内部推理。
- 每次更换测试问题，导致改版前后无法比较。
