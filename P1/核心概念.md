# Phase 1 核心概念

这一节的目标不是把术语背下来，而是先建立一个足够实用的直觉：你知道这些概念分别在控制什么，遇到问题时该往哪里调。

---

## 1. LLM 核心概念


Tuned LLM（微调/对齐后的大语言模型）​ 和 Base LLM（基座/预训练大语言模型）​ 的主要区别如下：

一、Base LLM（基础预训练模型）

是什么：经过大规模无标注文本自监督预训练（通常是预测下一个词 Next Token Prediction）得到的原始语言模型。

例：LLaMA-2-7B（原始版）、GPT-3（原始未对齐版）

特点：

✅ 掌握语法、事实知识、逻辑推理能力

❌ 不会主动遵循指令（问"总结一下""翻译成英文"，它可能只是续写句子）

❌ 可能输出有害、偏激或无意义内容

更像是"博学的文本补全器"，而不是对话助手

用途：作为进一步微调的基础，或用于特定研究/文本续写任务

二、Tuned LLM（微调 / 对齐模型，如 SFT / RLHF）

是什么：在 Base LLM 基础上，用指令数据（SFT）和/或人类反馈强化学习（RLHF/DPO）进行额外训练后的版本。

例：ChatGPT（GPT-3.5/4 after RLHF）、LLaMA-2-Chat、Qwen-Chat、Claude

特点：

✅ 理解并遵循人类指令（问答、总结、写代码等）

✅ 多轮对话、角色一致

✅ 更安全，减少有害输出

❌ 相对 Base Model 可能在某些纯知识回忆或创意发散上略受限

用途：实际产品——聊天机器人、Copilot、客服、写作助手等

### 1.1 LLM 的输入输出机制

LLM 的一次调用，本质上可以理解成：**把一组消息交给模型，模型根据这些消息预测并生成下一段文本。**

在应用开发里，我们通常不会只给模型一段孤立的文字，而是会把不同角色的消息一起传进去。常见输入包括：

- **System Message**：系统提示词，用来定义模型的角色、行为边界和输出要求
- **User Message**：用户当前提出的问题或任务
- **Assistant Message**：历史对话中模型之前的回答，用来维持多轮上下文
- **Tool Message**：工具调用后的返回结果，比如搜索结果、数据库查询结果、计算结果

这些消息会按顺序组成模型这一次能看到的上下文。模型并不是“记得”之前发生过什么，而是因为你把历史消息再次放进了本次请求里，它才表现得像有记忆。

一个典型流程是：

1. 应用程序准备消息列表，比如系统提示词、历史消息和当前用户输入
2. 客户端把消息、模型名、温度、最大输出长度等参数发给模型 API
3. 模型读取上下文，逐个生成输出 Token
4. API 返回模型生成的内容，可能是普通文本、JSON、工具调用请求，或流式 Token
5. 应用程序解析结果，再决定展示给用户、继续调用工具，还是进入下一轮对话

**例子：**

```python
messages = [
    {"role": "system", "content": "你是一个耐心的 Python 老师。"},
    {"role": "user", "content": "请用一句话解释什么是函数。"},
]

response = client.chat.completions.create(
    model=settings.model,
    messages=messages,
    temperature=0.3,
)
```

这个例子里，模型的输入不是单纯的“请解释函数”，而是同时包含了系统提示词和用户问题。因此输出会更倾向于“教学风格”，而不是随意回答。

#### 输入会影响什么

LLM 的输出质量，很大程度上取决于输入里给了什么信息。

- 系统提示词会影响整体角色、语气和边界
- 用户问题越清晰，模型越容易给出可用答案
- 历史消息会影响多轮对话里的指代和上下文理解
- 工具结果会让模型基于外部事实回答，而不是只靠自身参数里的知识
- 示例和格式要求会影响输出结构，比如 Markdown、JSON、表格

所以做 LLM 应用时，真正要设计的不是一句 Prompt，而是“本次请求里应该放哪些信息、按什么顺序放、放多少”。

#### 输出可能是什么

LLM 的输出不一定只是自然语言回答，常见形式包括：

- **普通文本**：解释、总结、改写、翻译
- **结构化数据**：JSON、表格、符合 Pydantic 模型的字段
- **工具调用请求**：模型判断需要调用哪个函数，以及传什么参数
- **流式输出**：模型一边生成一边返回 Token，适合聊天界面

在 Agent 系统里，模型的一次输出经常不是最终答案，而是一个中间决策。例如模型可能先输出“我要调用天气工具”，应用执行工具后，再把结果放回消息列表，让模型继续生成最终回答。

#### 一个重要直觉

LLM 不是传统意义上的函数：

```text
固定输入 -> 固定输出
```

它更像是一个受上下文和采样参数影响的生成器：

```text
消息列表 + 模型参数 + 上下文窗口限制 -> 生成结果
```

这也是为什么同一个问题，换系统提示词、换历史消息、调高 Temperature、增加 Few-shot 示例，都可能得到不同答案。

---

### 1.2 Token

可以把 Token 理解成模型处理文本时使用的“最小计数单位”。它不是严格等于“一个字”或者“一个单词”，而是模型分词后的片段。

- 在英文里，一个单词有时是 1 个 Token，有时会被拆成多个 Token
- 在中文里，通常一个字常常接近一个 Token，但也不是绝对一一对应
- 标点、空格、换行，也可能占用 Token

为什么它重要？因为模型的输入和输出，几乎都和 Token 数量直接相关。

- **费用**：很多模型按 Token 计费，输入多少、输出多少都会影响成本
- **速度**：输出 Token 越多，生成通常越慢
- **上下文限制**：一次能塞进模型的内容，最终也是按 Token 算

可以把它想成“模型看的字数预算”。预算越大，模型一次能看到的信息越多；预算越小，就越容易遗漏上下文。

**例子：**

如果你给模型一段很长的会议记录，再要求它总结重点，模型并不是按“页数”看，而是在按 Token 数量判断这段内容能不能装进当前上下文窗口。

---

### 1.3 Temperature

Temperature 决定模型输出时“保守”还是“发散”。

- **Temperature 低**：模型更倾向于选择概率最高、最稳妥的答案
- **Temperature 高**：模型更容易尝试不同表达，输出更有变化，也更容易跑偏

可以把它理解成“模型回答时的随机性旋钮”。

- 调低：适合事实问答、结构化输出、代码生成、数据抽取
- 调高：适合创意写作、头脑风暴、广告文案

**直觉类比：**

- 低 Temperature 像一个谨慎答题的学生，只写最有把握的答案
- 高 Temperature 像一个更敢发散的学生，可能会给你惊喜，也可能会离题

**常见误区：**

- Temperature 高不代表“更聪明”，只是“更敢变化”
- Temperature 低也不代表一定“更正确”，只是更稳定、更可复现

---

### 1.4 Context Window

Context Window 就是模型一次对话里“能看到的总内容上限”。

这个“总内容”包括：

- 系统提示词
- 用户当前输入
- 历史对话
- 工具返回结果
- 模型已经生成的内容

这些内容加起来，不能超过模型的上下文窗口限制。

可以把它想成模型面前的一张工作台。工作台大小有限，你放进去的材料太多，后面的内容就放不下了。实际系统里通常会出现几种处理方式：

- 截断最早的历史消息
- 压缩历史内容，先做摘要
- 只保留和当前任务最相关的信息

**为什么它重要？**

- 对多轮对话很关键：上下文太长时，老消息可能被裁掉
- 对 Agent 很关键：工具返回内容太多，会挤占用户问题的空间
- 对 RAG 很关键：检索回来的文档片段太多，可能把窗口塞满

**例子：**

你做一个带记忆的聊天机器人，前面已经聊了 30 轮。如果不做滑动窗口或摘要，后面的新问题可能根本放不进去，或者旧上下文会被自动截断，导致模型“失忆”。

---

### 1.5 模型选型

模型选型本质上是在做 trade-off，也就是权衡。

通常要在下面几个维度之间平衡：

- **效果**：回答质量、推理能力、代码能力、遵循指令能力
- **成本**：每次调用多少钱
- **速度**：响应是否够快，用户等不等得起
- **上下文长度**：能处理多长的输入
- **稳定性**：结构化输出是否稳定，是否容易跑偏
- **多模态能力**：是否支持图片、音频、文件

一个实用判断方法是：先看任务，再选模型，而不是先迷信“最强模型”。

#### 常见场景怎么选

**1. 简单分类 / 抽取 / 改写**

- 优先考虑便宜、快的小模型
- 因为任务规则明确，不一定需要最强推理能力

**2. 复杂分析 / 代码生成 / 长链路 Agent**

- 更适合能力更强的模型
- 因为中间步骤多，对指令遵循、推理和稳定性要求更高

**3. 大上下文问答**

- 优先关注上下文窗口大小
- 否则再强的模型也装不下材料

**4. 面向用户的实时对话**

- 速度通常和质量同样重要
- 很多场景宁可略降一点质量，也要换更快的响应

#### 一个很实用的选型思路

先用下面这 4 个问题筛：

1. 这个任务最在意质量、速度还是成本？
2. 任务需不需要复杂推理，还是模板化处理就够了？
3. 输入会不会很长？
4. 输出需不需要很稳定，比如固定 JSON？

如果你还拿不准，最稳妥的方式不是拍脑袋，而是：

- 选 2 到 3 个候选模型
- 用同一组测试样例跑一遍
- 对比质量、耗时、成本
- 再决定默认模型

这比只看网上排行榜更靠谱，因为真正决定效果的，是“这个模型在你的任务上表现如何”。

## 2. Prompt 设计模式

Prompt 设计模式可以理解成“你怎样向模型下指令”。同一个模型，Prompt 写法不同，输出质量可能差很多。

下面这几种模式，是最常见也最值得掌握的基础套路。

### 2.1 Zero-shot

Zero-shot 就是：**不给例子，直接提要求。**

模型只靠它本身学到的知识和你当前的指令来回答。

**例子：**

```text
请把下面这段用户评论分类为正面、中性或负面，并给出一句理由。
评论：这家店上菜很慢，但味道不错。
```

**适合场景：**

- 任务比较简单
- 指令边界比较明确
- 你想先快速试一下模型表现

**优点：**

- 写起来最快
- 成本低，不占太多上下文

**缺点：**

- 模型可能理解偏了你的格式或标准
- 对复杂任务稳定性一般

可以把 Zero-shot 理解成：你第一次把任务交给一个新同事，只说目标，不给参考样例。

---

### 2.2 Few-shot

Few-shot 就是：**先给模型几个示例，再让它照着做。**

这些例子本质上是在告诉模型：

- 你想要什么格式
- 你用什么标准判断对错
- 你期望怎样的语气和粒度

**例子：**

```text
请将用户评论分类为正面、中性或负面。

示例1：
评论：物流很快，包装完整。
输出：正面

示例2：
评论：东西一般，不算差，也没惊喜。
输出：中性

现在请处理：
评论：这家店上菜很慢，但味道不错。
输出：
```

**适合场景：**

- 分类标准不够直观
- 输出格式需要统一
- 你发现 Zero-shot 结果不稳定

**优点：**

- 稳定性通常比 Zero-shot 更好
- 对格式控制更有效

**缺点：**

- 占用更多上下文
- 示例选不好，模型也会被带偏

可以把 Few-shot 理解成：你不只是交代任务，还给了对方几份“参考答案”。

---

### 2.3 任务分解与结果验证

复杂任务通常需要分解，但工程目标不是要求模型公开隐藏的 Chain-of-Thought，而是让应用获得**可检查的中间产物和最终结果**。

它适合需要多步处理的任务，比如：

- 数学题
- 多步逻辑判断
- 复杂信息抽取
- 需要先分析再得出结论的问题

**例子：**

```text
请先输出计算计划，再输出最终价格，并用代码重新计算验证结果。
问题：一个商品原价 200 元，先打 8 折，再减 20 元，最终价格是多少？
```

这种方式的核心不是让模型“多说思考过程”，而是把计划、工具结果、引用或校验结果设计成应用可以检查的输出。

**优点：**

- 可把复杂任务拆成能够验证的步骤
- 可以用代码、工具或引用检查结果

**缺点：**

- 工作流更长，成本和延迟可能增加
- 不是所有简单任务都值得拆分

**一个重要提醒：** 如果简单分类可以通过 Schema 和确定性校验完成，就不要增加多步推理。只有当评估结果显示复杂任务确实需要规划、工具或验证时，才增加这些步骤。

---

### 2.4 ReAct

ReAct 是 Reason + Act 的组合，也就是：**先推理，再行动；拿到结果后，再继续推理。**

它特别适合 Agent，因为 Agent 不只是“想”，还要“做”。

一个典型 ReAct 流程通常像这样：

1. 模型先判断现在需要什么信息
2. 如果现有信息不够，就调用一个工具
3. 拿到工具结果后，再继续分析
4. 最后给出答案

**例子：**

用户问：`今天上海适合穿短袖吗？`

模型如果直接猜，容易不准。ReAct 的做法会更像：

1. 我需要先知道上海今天的天气和温度
2. 调用天气工具查询上海天气
3. 根据工具返回的温度、降雨、风力做判断
4. 再回答用户是否适合穿短袖

所以 ReAct 的核心不是“回答更长”，而是“在需要时先查、先算、先调用工具”。

**适合场景：**

- 需要外部信息才能回答的问题
- 需要调用搜索、数据库、计算器、文件系统等工具
- 多步任务执行

**优点：**

- 比纯靠模型脑补更可靠
- 能把模型能力和外部工具能力结合起来

**缺点：**

- 系统实现更复杂
- 工具设计不好时，整体效果会明显下降

可以把 ReAct 理解成：一个人遇到不会的问题，不是硬猜，而是先去查资料、用工具，再回来回答。

---

### 2.5 常见 Prompt 模式总结

| 模式 | 核心做法 | 适用场景 |
|---|---|---|
| Zero-shot | 直接提要求，不给示例 | 简单问答、改写、翻译、分类、快速试验 |
| Few-shot | 给几个输入输出示例，让模型照着做 | 格式要求明确、分类标准细、希望输出风格稳定 |
| 任务分解与验证 | 产出可检查的计划、工具结果或校验结果 | 数学、检索、多步分析、复杂决策 |
| ReAct | 让模型边推理边调用工具 | Agent、搜索、查数据库、计算、文件操作等外部任务 |
| Role Prompt | 给模型设定角色 | 教学、咨询、客服、代码审查、专业风格输出 |
| Structured Prompt | 明确规定输出格式 | JSON、表格、Pydantic 结构化输出、自动化程序解析 |
| Constraint Prompt | 明确限制边界 | 字数限制、语气限制、安全边界、禁止编造 |
| Iterative Prompt | 多轮修改和反馈 | 写作润色、方案打磨、代码迭代、复杂内容生成 |

这些模式不是互斥的。实际写 Prompt 时，经常会把几种方式组合起来：比如先设定角色，再给输出格式，最后补充字数、语气和安全边界。

---

## 3. 这几种 Prompt 模式怎么选

如果你刚开始做 Prompt 设计，可以先用这个简单判断：

- **任务简单、先快速试验**：用 Zero-shot
- **输出格式不稳、分类标准不清**：加 Few-shot
- **问题需要多步处理**：加入可检查的任务分解和结果验证
- **需要调用工具或外部信息**：用 ReAct

一个常见的工程实践顺序是：

1. 先从 Zero-shot 开始
2. 结果不稳，再补 Few-shot
3. 如果问题需要多步处理，再加入计划、工具或校验节点
4. 如果模型必须查资料或调用工具，再进入 ReAct / Agent 方案

这比一上来就堆很复杂的 Prompt 更高效。

---

## 4. 一句话总结

- **LLM 输入输出机制**：应用把消息列表和参数发给模型，模型基于上下文逐步生成文本、结构化数据或工具调用
- **Token**：模型处理文本时的计数单位，影响成本、速度和长度限制
- **Temperature**：控制输出的随机性，高了更发散，低了更稳定
- **Context Window**：模型一次能看到的总信息上限
- **模型选型**：在效果、成本、速度、上下文长度之间做权衡
- **Zero-shot**：不给例子，直接提要求
- **Few-shot**：给几个示例，让模型照着学
- **任务分解与验证**：把复杂任务拆成应用能够检查的中间产物
- **ReAct**：让模型在推理过程中调用工具、获取外部信息再继续回答

## instrutor 库
instructor 是一个用于结构化输出（Structured Output）的 Python 库。它的核心功能是让你能够轻松地使用 Pydantic 模型来定义和约束大型语言模型（LLM，如 OpenAI GPT、Anthropic Claude 等）的输出格式。

简单来说，它把“让 LLM 返回 JSON”这件事变得非常简单、可靠和类型安全。

> 大模型的“结构化输出”本质上不是模型天生会“按 JSON 语法执行程序”，而是通过提示约束、解码约束和结果校验这三层一起实现的。
